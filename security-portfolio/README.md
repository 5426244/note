## 一些我认为值得记录的技术细节

**1. 判断列数不是靠猜**
`order by` 从 1 开始递增，直到报错，报错前一个数字就是列数。`order by 2` 正常、`order by 3` 报错 → 2 列。

**2. 端口开放 ≠ 端口暴露**
`ss -tlnp` 里 `LISTEN 127.0.0.1:3306` 和 `LISTEN *:80` 的风险等级完全不同。前者只有本机能连，后者整个网段都能访问。判断依据是**监听地址**，不是端口本身。

**3. XSS 要先判断注入上下文**
`<script>alert(1)</script>` 落在 `<div>` 里会执行，落在 `<option>` 或属性值里不会。DOM 型里 payload 被困在 `<select>` 内时，需要 `</option></select>` 先跳出容器。

**4. 只校验客户端字段等于没校验**
文件上传 Medium 难度只检查 `Content-Type`，而这是客户端可控的字段。用 Burp 把它从 `application/x-php` 改成 `image/jpeg` 就能绕过。

**5. 报告里没验证的事不下结论**
写“待确认”比写一个错的结论强。这是我在做资产梳理时体会最深的一条。

**6. “包含”不等于“等于”**
DVWA CSRF 的 Medium 用 `stripos($referer, $server_name)` 判断来源。只要 Referer 里任意位置出现服务器名就放行，于是 `192.168.59.128.evil.com`（攻击者自己的子域名）也能通过。
字符串匹配的安全判断，永远要问一句：能不能构造出“包含但不等于”的输入？

**7. 黑名单的漏洞在于“写不全”，不在“写错”**
DVWA 命令执行 High 的过滤数组里写的是 `'| '`（竖线**加空格**）。攻击者用不带空格的 `127.0.0.1|whoami` 直接绕过。黑名单的困境是：防御方必须穷举所有写法，攻击方只需找到一个漏网的。

**8. 反弹 shell 的两行红字不是失败**
`bash: cannot set terminal process group ... Inappropriate ioctl for device` 是 `bash -i` 在没有 TTY 的连接里必然出现的提示。判断成功的唯一标准是提示符变成 `www-data@kali`。
